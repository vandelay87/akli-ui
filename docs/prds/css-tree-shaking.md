# PRD: Per-Component CSS Tree-Shaking

> Companion PRD: `akli-ui-adoption.md` in `personal-website`, which currently accepts two permanent CSS-payload costs (Card's lost route-level code-splitting, `animations.css` keyframe duplication) as unavoidable consequences of this package's current CSS packaging. This PRD removes the need for those exceptions. Release this as v2.0.0 and get it live on npm *before* that PRD's migration begins, so personal-website builds against the new contract directly instead of migrating off the old one first.

## Overview

`@akli-dev/ui` ships one compiled `dist/index.css` containing every component's styles, regardless of which components a consumer actually imports. This PRD changes the build so a consumer's own bundler tree-shakes component CSS the same way it already tree-shakes the JS — `import { Button } from '@akli-dev/ui'` ships only `Button`'s compiled styles. Ships as a v2.0.0 breaking change to the documented CSS-import contract.

## Problem Statement

`src/index.ts` is a single barrel JS entry point; Vite's library-mode build compiles its entire import graph — every component's `.module.css` — into one file. A consumer must import that file globally and unconditionally, so importing a single component still ships the whole library's CSS. Concretely: personal-website's `Card` is used only on its lazy-loaded admin `Login` route today, so `Card`'s CSS currently ships only in that route's async chunk — sourcing `Card` from `@akli-dev/ui` as currently built would permanently move its styles into a globally-eager file loaded on every page. JS tree-shaking already works correctly here (verified by `.size-limit.json`'s per-component import budgets); CSS has no equivalent mechanism, and no gate measures it today.

## Goals

- `import { X } from '@akli-dev/ui'` ships only `X`'s own compiled CSS, plus exactly one copy of any CSS `X` genuinely shares with other components — never zero copies (missing styles) and never N copies (duplicated bloat)
- The public JS import path is unchanged: `src/index.ts` stays the sole barrel export. This does not reopen the barrel-vs-per-component-subpath decision already settled in issue #3
- A new automated gate exists to catch a future regression in either direction — no gate measures CSS output today, only JS
- Consumers can adopt this with zero required code changes beyond dropping the now-optional `@akli-dev/ui/index.css` import

## Non-Goals

- `src/styles/formField.module.css` — composed only by `Input` (single consumer, confirmed via grep). No duplication risk exists for a file with exactly one consumer; no change needed.
- `src/styles/stateBox.module.css` and `src/styles/text.module.css` — confirmed via grep to have **zero** consumers anywhere in this package's own `src/components/*/*.module.css` today. Since nothing imports or composes from them, they aren't even part of the current `dist/index.css` output. Out of scope entirely — do not treat this PRD as license to "clean these up," per `CLAUDE.md`'s own pitfall note that "no consumer in this package's own `src/`" isn't the same claim as "unused" (personal-website may hold similarly-named but unrelated local files).
- Reopening the barrel-vs-per-component-subpath JS export decision from issue #3 — the public API shape doesn't change, only how CSS is packaged underneath it.
- Any change to Storybook's CSS loading — confirmed `.storybook/preview.ts` imports directly from `src/`, not `dist/`, so Storybook is structurally unaffected by this change.
- Migrating personal-website itself — that's `akli-ui-adoption.md`'s job. This PRD unblocks it but doesn't implement it.
- JS bundle-size work — already solved and gated via `check:bundle-size`. This PRD is CSS-only.

## User Stories

- As a consumer of `@akli-dev/ui`, I want importing one component to ship only that component's CSS, so using this package doesn't force every page to load styles for components I never render.
- As a maintainer of `@akli-dev/ui`, I want an automated gate that fails if a future change reintroduces CSS bloat or breaks the shared-CSS dedup, the same way `check:bundle-size` already protects JS tree-shaking.

## Design & UX

No visual or behavioral change for any component — this is purely a build/packaging change. The observable difference is entirely in what a consumer's own build output contains: less unused CSS. The one consumer-facing contract change is documented in Technical Considerations (README rewrite) and is a "does less work now, not different work" change — dropping a previously-required import.

## Technical Considerations

### Why this design, not a naive one

The intuitive-but-wrong approach is per-component CSS files a consumer must manually import (e.g. `import '@akli-dev/ui/Button.css'` alongside the JS import) — this is what older libraries like early Ant Design did, and it's exactly the kind of DX papercut (forget the CSS import, get an unstyled component with no error) that this PRD should not reintroduce. Instead, use `rollupOptions.output.preserveModules: true` (each source module becomes its own output file, instead of the whole graph collapsing into one) combined with `vite-plugin-lib-inject-css` (detects each preserved module's compiled CSS and injects a real `import './X.css'` statement directly into that module's own compiled JS). A consumer's tree-shaking of the JS then naturally drops the paired CSS import too — zero extra ceremony, and the public JS import path (`src/index.ts` as the sole barrel) doesn't change at all, since `preserveModules` splits a single entry's dependency graph into per-module chunks without requiring separate declared entries per component.

`vite.config.ts`'s own existing comment on `build.lib.entry` already namechecks `vite-plugin-lib-inject-css` as solving "a different problem... than what v1 needed" — v1's goal was "ship one global stylesheet," which this PRD's goal (tree-shakeable per-component CSS) now supersedes. That comment gets a follow-up note explaining the change in goal, so a future reader doesn't read the two as contradicting each other.

### The one real risk, and why it's already de-risked

`src/styles/interactions.module.css` (277 lines) is composed cross-file via CSS Modules `composes: X from '...'` by six components: `Button` (`.focusRing`), `Header` (`.focusRing`, two usages), `ThemeToggle` (`.focusRing`), `Loading` (`.spinner`), `Link` (`.focusRing`, `.linkIcon`, `.nudgeRight`, `.nudgeLeft`, `.nudgeUpRight`), and `Input` (`.fieldFocusRing`). Under `preserveModules`, each of these becomes an independently-split output chunk with no shared parent chunk — exactly the condition under which cross-file `composes:` duplicates its source verbatim into every consumer, rather than being hoisted into one shared file.

This isn't a newly-discovered risk: **`interactions.module.css`'s own header comment already documents this exact failure mode in general form**, and **`Card.tsx` already implements the fix** — `Card` doesn't `composes:` from `interactions.module.css` at all; it does a real JS `import interactions from '../../styles/interactions.module.css'` and merges classes at render time via `cx()` (`src/utils/cx.ts`). A real JS import gives the bundler a genuine, independently-addressable module to hoist into its own single output chunk — a CSS-level `composes:` doesn't. So the dedup half of this problem isn't a novel risk; it's applying an already-proven pattern to the six remaining components that still take the CSS-level shortcut.

**But Card's precedent only covers additive composition, not override correctness — two of the six components need the latter and the PRD must not treat this as solved by analogy.** Card's uses of `interactions.surfaceHover`/`interactions.focusRing` never redeclare a property the composed rule also sets. Two of the six components being refactored do:
- `Loading.module.css`'s `.spinner` redeclares `width`, `height`, `border-width`, `border-inline-end-color` on top of the composed `interactions.spinner` rule — same class, same specificity.
- `Input.module.css`'s `.invalid:focus-visible` redeclares `border-color`/`box-shadow` on top of the composed `.fieldFocusRing:focus-visible` — an exact specificity tie the file's own comment says is deliberate ("overrides `.fieldFocusRing`'s accent-colored one for this state").

Today, correctness for both depends entirely on `composes:`'s guarantee that the composed file's rules are always emitted *before* the local file's in the same compiled output, so the local, later-declared rule wins the cascade tie. Once `interactions.module.css` and each component's own CSS become independently-chunked files merged only via `cx()`-joined class names, that guarantee disappears — **class-attribute order has no effect on CSS cascade resolution; only stylesheet/rule emission order does**, and nothing in the proposed toolchain (`vite-plugin-lib-inject-css`'s injection order relative to a component's own real CSS import) is documented to preserve today's implicit ordering. This is not covered by the dedup-focused spike checks below, and `vitest-axe` (jsdom, checks the accessibility tree, not computed styles or cascade) would not catch a regression here either.

**Fix, folded into Phase 1 below for these two components specifically:** don't rely on import/assembly order. Raise local specificity explicitly so the override wins regardless of load order — e.g. `Loading`'s override becomes a compound selector like `.spinner.large` (or an `!important`-free specificity bump appropriate to the actual variant structure), and `Input`'s becomes `.field.invalid:focus-visible` rather than a bare `.invalid:focus-visible` tied against `.fieldFocusRing:focus-visible` on equal footing. Verify the result with a real-browser or Storybook (`addon-a11y`'s underlying real-browser render, both themes) computed-style check — not `vitest-axe` — confirming `Loading`'s large/two-tone spinner sizing and `Input`'s invalid+focused border/box-shadow render identically to today.

**One component is lower-risk than its composed-class count suggests, worth correcting the intuition:** `Link` composes 5 classes but 3 (`.icon`, `.nudgeRight`, `.nudgeLeft`, `.nudgeUpRight` — actually all of `linkIcon`/`nudgeRight`/`nudgeLeft`/`nudgeUpRight`) are empty local aliases with no CSS of their own, safely deletable in favor of referencing `interactions.*` directly; the remaining `.link`/`focusRing` composition never overlaps in property with the composed rule. Breadth of `composes:` usage isn't the same signal as override risk — Loading and Input (one composed class each) are the two that actually need care.

### Phase 1 — Refactor `composes:` to the `Card` pattern (ships independently, no consumer-visible change)

For `Button`, `Header`, `ThemeToggle`, `Link`: remove `composes: X from '../../styles/interactions.module.css'`; add `import interactions from '../../styles/interactions.module.css'` in the component's `.tsx` and merge classes at render time via `cx()`, matching `Card.tsx` exactly — these four are purely additive (no local rule overrides a property the composed rule also sets), so the `Card` precedent applies directly. For `Link` specifically, delete the empty local aliases (`.icon`, `.nudgeRight`, `.nudgeLeft`, `.nudgeUpRight` — each currently nothing but a `composes:` line) and reference `interactions.linkIcon`/`interactions.nudgeRight`/etc. directly rather than keeping a pass-through local class.

For `Loading` and `Input`: same JS-import + `cx()` conversion, **plus** raise the overriding local rule's specificity so it wins independent of load/import order (see the cascade-order risk above) — e.g. `Loading`'s size/color override becomes a compound selector rather than relying on emission order beating a bare `.spinner`, and `Input`'s becomes `.field.invalid:focus-visible` rather than a bare `.invalid:focus-visible` tied against `.fieldFocusRing:focus-visible`. `Input`'s separate `composes: field from '../../styles/formField.module.css'` is untouched (single consumer, out of scope).

Re-run each component's existing `vitest-axe` coverage as a safety net for all six, but for `Loading` and `Input` specifically, also verify with a real-browser check (Storybook, both themes) that computed styles are unchanged — `vitest-axe` checks the accessibility tree, not computed styles, and would not catch a cascade-order regression.

### Phase 0 — Spike (mirrors this repo's own precedent from issue #3's build-architecture spike and issue #12's consumer-integration verification)

This spike carries more genuine uncertainty than "verify the obvious" — independent research confirms `vite-plugin-lib-inject-css`'s `preserveModules` support is real but recent (fixed in v2.2.0 after previously *silently* skipping CSS injection with no build error, per that plugin's own issue tracker) and has never been exercised by its author or community against Vite 8's Rolldown-based bundler specifically (its whole history is against Rollup-based Vite 5). Pin the plugin to `^2.2.0` or later explicitly in Phase 2 — an unpinned or older resolution reintroduces the exact silent-failure mode this design is meant to avoid.

On a scratch branch, before touching the real feature branch: add `vite-plugin-lib-inject-css@^2.2.0`, set `preserveModules: true` and `preserveModulesRoot: 'src'`, apply Phase 1's refactor to `Button` only first. Build, then:
1. Inspect `dist/` directly: confirm `interactions.module.css` emits as its own single output CSS file, referenced by an *injected* import in `Button`'s own compiled JS — not inlined into it. Explicitly confirm the plugin's internal data source (`chunk.viteMetadata.importedCss`, a Vite-internal, not native-Rollup/Rolldown, chunk property) is actually populated at the point the plugin reads it — don't just check the end result, since a silent-empty-metadata failure is exactly the documented pre-2.2.0 bug class.
2. Verify output file naming: does the existing `build.lib.fileName: '[name]'` (designed around today's 4 fixed named entries) still produce the expected `dist/components/<Name>/<Name>.js` structure under `preserveModules`, matching `unplugin-dts`'s independently-computed `.d.ts` output paths 1:1 — or does this need `rollupOptions.output.entryFileNames` instead (the more commonly-documented pairing with `preserveModulesRoot`)? Resolve this by inspection, not assumption.
3. Check whether the `index` entry still produces a literal `index.css` asset once its own CSS is split per-component — it may not, once nothing but `animations.css` is left at the entry level — and confirm `assetFileNames`'s `cssEntryNames` set (which special-cases exactly the 3 known fixed CSS entry names) doesn't silently become a dead membership test as a result.
4. Build a throwaway scratch consumer whose `main.tsx` imports only `{ Button }`, using the same method as the Phase 3 CI gate below (`npm pack` the built package into a tarball, install it fresh into an ephemeral directory — not a `pnpm link`/`file:` source-tree link, which can mask real resolution behavior and doesn't respect `files`/`exports`/`sideEffects` the way a real npm consumer install does). Make the consumer itself a small Vite app, matching the real target consumer (personal-website). Inspect its actual build output: exactly one copy of an `interactions.module.css`-only rule (grep-count == 1, not 0, not 6), and zero bytes from any non-imported component's CSS.
5. Critically, verify `vite-plugin-lib-inject-css`'s injected import path matches the *actual, possibly-hashed* filename the build assigns — a mismatch would 404 in a real consumer build; this is the single highest-value thing this spike must catch empirically, not assume.
6. Repeat steps 1–5 for the remaining five composing components (with steps 2 and 4 including a real-browser/Storybook computed-style check for `Loading` and `Input` specifically, per the cascade-order risk above — not just `vitest-axe`), plus one component with no shared-CSS dependency (e.g. `Typography`) to confirm it emits no/near-empty CSS and pulls in nothing beyond `animations.css`.
7. Also build a scratch consumer importing `{ Button, Header, Link }` together (multiple `interactions.module.css` consumers at once) and confirm the shared rules still appear exactly once, not three times.
8. Re-run `check:bundle-size` against this spike's build. Its existing per-component KB budgets were calibrated against today's single-bundle structure; the barrel → per-module re-export indirection `preserveModules` introduces is a plausible (if small) source of tree-shaking/interop-wrapper deltas. Confirm budgets still hold, or recalibrate them as part of this PRD rather than discovering a budget failure later as an unrelated-looking CI break.
9. Record this spike's pass/fail results in writing in the real feature-branch PR's description before Phase 2's changes are proposed for review — not just as scratch-branch commit history that gets discarded.

**Fallback**, only if `vite-plugin-lib-inject-css` doesn't treat a CSS-Modules-only file (no exported JS bindings beyond the CSS Modules proxy object) as a real chunk under `preserveModules`, or step 1's `chunk.viteMetadata` check comes back empty under Rolldown: promote `interactions.module.css` to a fourth standalone, always-loaded CSS entry in `build.lib.entry` — the same treatment `tokens.css` already gets (add to `cssEntryNames`, export at a new path, document in the README's required-imports list). This is cheap and low-risk given its size (277 lines, shared by 6 of ~14 components) and mirrors an already-proven pattern in this exact `vite.config.ts`. Phase 1's refactor (including the Loading/Input specificity fix) is worth keeping regardless of which path wins — it's what makes `Card` correctly deduplicate today, too, and the specificity fix is correct hygiene independent of the CSS-splitting mechanism.

### Phase 2 — Build configuration

- **`vite.config.ts`**: add `vite-plugin-lib-inject-css@^2.2.0` (pinned floor — see Phase 0) to `plugins`; add `rollupOptions.output.preserveModules: true` and `preserveModulesRoot: 'src'`, and switch `build.lib.fileName`/naming to whatever the spike (Phase 0 step 2) confirms actually produces the expected per-component output structure (likely `rollupOptions.output.entryFileNames`, the more commonly-documented pairing with `preserveModulesRoot`, rather than the existing `lib.fileName: '[name]'` which was designed around a small fixed entry set). Update the existing `build.lib.entry` comment (which already namechecks this exact plugin) with a follow-up note on why v2's goal changed from v1's. `assetFileNames` needs the Phase 0 step 3 check (does `index.css` still exist as a real asset) before assuming no code change is needed. `unplugin-dts`'s `entryRoot`/alias-rewrite handling already mirrors `src/`'s structure 1:1 and should extend cleanly, but per issue #12's own established caution against assuming interacting Vite-lib-mode config "just works," confirm dist `.d.ts` paths didn't regress to the pre-fix `../../../../src/components/X`-style output once chunking granularity changes. `rollupOptions.external` (peerDeps-derived) is unaffected. Note on `base: './'`/font handling: `preserveModules` is technically a global `rollupOptions.output` setting, not scoped to any one declared entry — but `tokens.css`/`fonts.css` are standalone CSS-as-raw-input entries with no JS module graph of their own for `preserveModules`'s chunking logic to act on, so the practical conclusion (unaffected) still holds; the reasoning is corrected here so it isn't read as "preserveModules is scoped per-entry," which it isn't.
- **`package.json`**: new devDependency `vite-plugin-lib-inject-css`. `sideEffects: ["*.css"]` stays — now more load-bearing than before, since a consumer's bundler must be told every per-component `.css` file is a side effect rather than something safely elided just because nothing imports a named binding from it.
- **`exports` map**: keep `./index.css` as an export key, pointed at `dist/index.css` — its content shrinks to just `animations.css`'s keyframes once per-component CSS moves out. Don't remove or rename the key: this is already a breaking release, and letting a consumer's stale `import '@akli-dev/ui/index.css'` become harmless/tiny rather than a hard 404 minimizes migration friction. Document it in the README as no longer required but safe to leave in place.

### Phase 3 — New regression gate (this PRD's actual proof of done — nothing measures CSS output today)

Two automated layers, both added to CI's existing `check` job alongside `check:bundle-size`:
1. **Structural dist inspection** — a new `scripts/check-css-tree-shaking.ts`, mirroring the existing `scripts/check-mdx-docs-render.ts` convention (standalone script, its own `pnpm check:*` entry). After `vite build`, it asserts each component's own CSS output exists and contains only its own rules (no cross-component leakage — checked by grepping for known per-component class-name fragments, not by literal byte-counting, since a build will never be zero bytes overall due to legitimately shared CSS), and greps the full `dist/` tree for an `interactions.module.css`-only fragment, asserting the count is exactly 1.
2. **Scratch-consumer integration check** — **not** a fixture checked into this repo with its own `node_modules`/lockfile (this repo isn't a pnpm workspace of multiple packages, and a source-tree `file:`/`link:` consumer reintroduces the "behaves differently locally vs. CI" problem, plus an unaddressed peer-dependency-drift risk if `react`/`vite`'s required versions change and nothing forces the fixture to follow). Instead: a CI step that `npm pack`s the just-built package into a tarball (this respects `files`/`exports`/`sideEffects` exactly, the way a real npm consumer's install does, unlike a raw source-tree link), installs it fresh into an ephemeral directory (`mktemp -d`, not committed to git) alongside a minimal Vite-based consumer app (matching personal-website, the real target consumer), builds that consumer importing only `{ Button }`, and asserts the same dedup/leakage properties from a genuine downstream bundler's perspective. This is what would catch a hashed-filename mismatch the structural check alone might miss, matching this repo's own precedent (issue #12) that "does this actually resolve correctly for a real consumer" needs verification against an actual install, not just an inspection of this package's own `dist/`. Confirm during implementation that branch protection actually requires this `check` job as a required status check — this PRD assumes it does but that wasn't independently verifiable during PRD review.

Update `CLAUDE.md`'s "Greppable gates" section with the new script(s), matching its existing one-line "what regression does this prevent" framing.

### Phase 4 — Docs and release

- **README**: "Required CSS imports" drops from three to two (`fonts.css` before `tokens.css`); `index.css` becomes optional/legacy, documented as such rather than removed from the docs entirely. Add a short "Migrating from v1" callout. Update the `Usage` code sample to drop the now-unnecessary `index.css` import line.
- **Changesets**: a major-bump changeset, with a summary explaining the behavior change (per-component CSS tree-shaking) and that `@akli-dev/ui/index.css` is no longer required (now contains only global animation keyframes) but remains safely importable. This is only the second-ever CHANGELOG entry (after 1.0.0's "Initial release"), worth being explicit and example-laden in since it sets the pattern for what a breaking-change entry looks like in this repo's history going forward.
- **Sequencing**: this must merge, go through the Version-Packages-PR → npm-publish flow, and be verifiably live on npm as `2.0.0` before personal-website's `akli-ui-adoption.md` migration begins its Phase A. "Verifiably live" means running `npm view @akli-dev/ui@2.0.0 version` and confirming it returns `2.0.0` — the release workflow's own success status is not sufficient evidence, since its single job (per `release.yml`) reports success on three different outcomes (a no-op merge with no pending changesets, opening/updating the Version-Packages PR, and the actual `npm publish`), and a green run doesn't distinguish "published" from "just updated the version PR." This exact verification idiom (`npm view "$package_name@$version" version`) already exists in `.github/scripts/release-publish.sh` — reuse it rather than inventing a new check. Once confirmed live, update the personal-website PRD's Phase A wording to target the new v2 contract directly and drop its accepted-cost language around Card's lost code-splitting and the `animations.css` duplication — both are resolved by this PRD.

### Testing

- Existing per-component `vitest-axe`/unit tests for the six refactored components must pass unchanged after Phase 1 (same runtime output expected).
- `check:bundle-size` (JS) must still pass — this PRD doesn't touch JS tree-shaking, only verifies it doesn't regress.
- `check:mdx-docs` and the full existing test suite/typecheck must still pass.
- The new `check:css-tree-shaking` gate (Phase 3) is the primary new test surface this PRD adds, and is itself part of the acceptance criteria, not optional polish.
- TDD is applicable to Phase 3's gate script itself (write the structural/consumer assertions against the *current*, known-broken behavior first, watch them fail, then make them pass via Phases 0–2) — less applicable to Phase 1's refactor, which is a mechanical, behavior-preserving transformation verified by existing tests rather than new ones.
